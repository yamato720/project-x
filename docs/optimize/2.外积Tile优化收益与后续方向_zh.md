# Project-X：外积 Tile 优化收益与后续方向

这份文档记录两件事：

1. 这次把外积从元素级 black-box 改成 `8x8 tile` black-box 之后，性能为什么明显提升。
2. 现在离纯 HLS 版本还剩哪些差距，下一步最值得继续优化什么。

## 2. 这次为什么会快

### 2.1 旧版本慢在哪里

旧版本的关键问题是：

- 外积阶段按元素调用 `outer_product_mul_bits`
- `outer_product_mul_bits` 是 `ap_ctrl_chain` black-box
- Vitis HLS 不允许这种 black-box 放进 pipeline region

所以外积虽然单次乘法本身只有：

```text
latency = 6
II = 1
```

但 HLS 外层仍然是在做：

```text
每个元素一次 black-box 调用
```

旧纯 HLS 报告能看到：

- [reports/hls/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt](/home/pyx/ProjectFS/Project-X/reports/hls/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt)

其中外积内层是：

```text
krnl_spmv_Pipeline_OuterProductColLoop
latency = 12 ~ 523 cycles
```

而之前 Chisel 路线最慢的地方，本质上就是：

```text
HLS 在外积双层循环上调度 black-box 的方式太细碎
```

### 2.2 新版本改了什么

这次改成了：

```text
outer_product_tile_bits(lhs_tile[8], rhs_tile[8]) -> out_tile[64]
```

也就是：

- 一次 black-box 调用直接计算 `8x8 = 64` 个外积元素
- HLS 外层 loop 不再对每个元素单独发一次 black-box
- 写回阶段再把 tile 内 64 个结果顺序写到 `yy_t`

调用次数大约从：

```text
512 * 512 = 262144 次
```

变成：

```text
(512 / 8) * (512 / 8) = 4096 次
```

也就是：

```text
black-box 调用次数下降 64 倍
```

这不会线性变成 `64x` 加速，但它成功把主瓶颈从：

```text
元素级 black-box 调度
```

变成：

```text
tile 级调用 + tile 写回 + 其余 HLS 外壳开销
```

所以收益很大，而且方向是对的。

## 3. 报告里怎么体现这次收益

### 3.1 `hybrid` 当前 HLS 视角

- [reports/hybrid/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt](/home/pyx/ProjectFS/Project-X/reports/hybrid/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt)

关键点：

```text
outer_product_tile_bits                   latency = 6 cycles, II = 1
krnl_spmv_Pipeline_OuterProductStoreTile  latency = 137 cycles
OuterProductColTileLoop                   latency = 151 cycles
```

这说明：

- black-box 自己很快
- 外积主循环已经不再是“每元素一次调用”
- 现在 tile 写回和 tile 外层调度开始变成新的可见成本

### 3.2 `chisel_core` 当前 HLS 视角

- [reports/chisel_core/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt](/home/pyx/ProjectFS/Project-X/reports/chisel_core/hw/xilinx_u55c_gen3x16_xdma_3_202210_1/krnl_spmv/hls_reports/krnl_spmv_csynth.rpt)

关键点：

```text
spmv_row_muladd_bits                      latency = 24 cycles, II = 1
outer_product_tile_bits                   latency =  6 cycles, II = 1
krnl_spmv_Pipeline_OuterProductStoreTile  latency = 137 cycles
```

这说明：

- `chisel_core` 的行级 SpMV 和外积 tile 都已经是固定流水算子
- 现在整体速度不再被“单元素外积 black-box”卡住
- 但 `chisel_core` 仍然没有明显超过 `hybrid`

## 4. 为什么 `hybrid` 和 `chisel_core` 现在还是差不多

当前结果里：

```text
hybrid      34.02 ms
chisel_core 35.11 ms
```

两者仍然很接近，原因也比较直接：

- 两者现在共同的大头还是外积阶段
- 两者外积都走同一个 `outer_product_tile_bits`
- `chisel_core` 额外把行级 SpMV 也换成了 `spmv_row_muladd_bits`
- 但行级 SpMV 的总工作量本来就远小于外积

也就是说：

```text
外积仍是主导项
```

所以哪怕 `chisel_core` 在行级 SpMV 上更“RTL 化”，它也不会自动比 `hybrid` 快很多。

## 5. 离纯 HLS 还差在哪

虽然提升明显，但现在和纯 HLS 还有一段距离：

```text
hls          6.24 ms
hybrid      34.20 ms
chisel_core 34.41 ms
```

主要差距在这几项。

### 5.1 外积写回仍然是串行风格

当前 tile black-box 算完之后，HLS 还要做：

```text
64 个结果逐个写到 yy_t
```

报告里可以看到：

```text
OuterProductStoreTile latency = 137 cycles
```

这已经不是旧版那种灾难性的元素级 black-box 调度了，但它仍然说明：

```text
tile 内结果输出到内存的组织成本不低
```

### 5.2 tile 粒度还是 8x8

`8x8` 是一个很好的第一版，因为它能快速验证方向。

但它的代价是：

- black-box 调用次数虽然降了 64 倍
- 但对 `512x512` 来说仍然有 `4096` 次 tile 调用

这已经比旧版好很多，但还不是特别粗的粒度。

### 5.3 `hybrid` 的 RowLoop II 不是 1

当前 `hybrid` 报告里：

```text
Pipelining result : Target II = 1, Final II = 3, loop 'RowLoop'
```

这说明 `hybrid` 的 HLS SpMV 行级流水本身也还有提升空间。

### 5.4 `chisel_core` 的额外收益还没覆盖封装成本

`chisel_core` 把行级 SpMV 也交给 `spmv_row_muladd_bits` 了，但因为：

- 外积仍然是更大的主导项
- HLS 外壳、tile 写回、内存访问没有一起“RTL 化”

所以这一步带来的收益暂时还不够大。

## 6. 下一步最值得做什么

优先级建议如下。

### 6.1 第一优先级：继续放大外积 tile

最值得继续试的是：

- `8x8 -> 16x8`
- `8x8 -> 8x16`
- 或直接 `16x16`

核心目的不是“看起来更大”，而是继续减少：

```text
tile 调用次数
```

同时把每次 black-box 调用摊薄到更多结果元素上。

需要注意的是：

- tile 越大，DSP 占用会继续上升
- 时序和布线压力也会明显增加

所以推荐顺序是：

1. 先试 `16x8` 或 `8x16`
2. 再看是否值得上 `16x16`

### 6.2 第二优先级：优化 tile 写回

当前 `OuterProductStoreTile` 已经是一个明确热点。

可考虑的方向：

- 让输出组织更贴合 HLS 写回模式
- 减少 tile 结果从 black-box 输出到 `yy_t` 的中间搬运
- 研究是否能把 tile 结果按更适合 AXI burst 的顺序产生

如果后续把 tile black-box 再做大，这一段会更值得优化。

### 6.3 第三优先级：单独优化 `hybrid` 的 RowLoop II

这主要影响 `hybrid`，因为它的行级 SpMV 还是 HLS 自己综合。

现在已经能看到：

```text
Target II = 1, Final II = 3
```

如果把这里压回 `II=1`，会对 `hybrid` 有额外增益。

### 6.4 第四优先级：把外积做成更流式的 Chisel core

这一步是更长期的路线。

不是继续暴力扩大 black-box 个数，而是把外积从：

```text
tile 级函数调用
```

再推进到：

```text
streaming outer-product engine
```

让 Chisel 接管：

- tile 内计算
- tile 内结果时序
- 更连续的输出组织

这一步工程量更大，但也是最接近纯 RTL 性能路线的方向。

## 7. 资源和时序上要注意什么

当前 `chisel_core` 的 HLS 估算里，`outer_product_tile_bits` 对应资源非常明显：

```text
outer_product_tile_bits DSP = 704
```

整体 `krnl_spmv` 估算：

```text
DSP = 771
```

也就是说，这次性能提升本质上是：

```text
用更多并行乘法资源，换更少的外积调度开销
```

这条路线是合理的，但后面每次再放大 tile，都要同时看三件事：

1. `kernel_min / kernel_avg / kernel_max`
2. DSP / LUT / FF 是否还能接受
3. routed timing 是否还稳

## 8. 一句话总结

这次性能明显提升，核心原因不是小修补，而是：

```text
把外积从元素级 black-box 调用，改成了 8x8 tile 级 black-box 调用
```

这一步成功移除了旧版本最致命的外积调度瓶颈，所以 `hybrid` 和 `chisel_core` 都获得了 `2x+` 提升。

下一步最值得继续投精力的，仍然是外积：

```text
更大的 tile
+ 更好的 tile 写回组织
+ 更流式的 outer-product engine
```

而不是优先继续细抠单个 FP64 multiply IP 本身。
